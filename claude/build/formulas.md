# 산출식

내재적 신뢰도 · 경험적 신뢰도 · 도구 설명 수위

# 6. 미결 사항 해소안

# 6.1 내재적 신뢰도 산출식 (§9 3번)

| 정책 | 산출식 | 근거 |
|---|---|---|
| `rule_based` | `0.50 + 0.30 · min(1, mᵢₙ)`<br>`mᵢₙ = minᵢ \|uᵢ − θᵢ\| / θᵢ` | 이용률이 임계값에 바짝 붙어 있으면 규칙의 이산 분기가 자의적 → 확신 낮음. 여유가 크면 분기가 명확. 범위 [0.50, 0.80] |
| `lstm_forecast` | `exp(−3 · ē) · 𝟙[in_distribution]`<br>`ē` = 최근 5회 `error`의 EMA (§4 ⑤ 정의) | 모델에 추론 시 dropout이 없어 분산 추정이 불가. 최근 실적이 유일하게 값싼 대리 지표. `ē=0.1 → 0.74`, `ē=0.3 → 0.41` |
| `dqn` | `σ(Q₍₁₎ − Q₍₂₎) · 𝟙[in_distribution]` | 상위 2개 Q값 마진. 2차 |

`rule_based`의 하한을 0.50으로 잡은 것은 의도적이다. **항상 가용한 안전 기본값**이므로 다른 정책이 전부 실패해도 이것 하나는 에스컬레이션 문턱(τ=0.45) 위에 있다. 이 상수가 곧 "언제 사람을 부를 것인가"의 하한을 정의한다.

첫 5스텝은 `ē` 표본이 없다. `lstm_forecast`는 `status="unavailable"` (history < 10)이므로 자연히 배제된다 — 별도 처리 불필요.

# 6.2 경험적 신뢰도 갱신식 (§9 4번)

```
r ← (1 − α)·r + α·s          α = 0.2,  s = 1 if sla_met else 0
n ← n + 1

effective = (r·n + r₀·m) / (n + m)      r₀ = 0.5,  m = 5
```

- **α = 0.2** — 반감기 약 3스텝. 시나리오가 전환되는 `mixed`(120스텝, 5회 전환)에서 전환 후 5~10스텝 내에 신뢰도가 따라붙는다. α가 작으면 `mixed`에서 자기 개선이 안 보이고, 크면 잡음을 학습한다.
- **축소 항 (m=5)** — `n`이 작을 때 `r`이 0 또는 1로 튀는 것을 막는다. 첫 성공 1회로 신뢰도 1.0이 되면 에이전트가 그 정책에 고착된다.
- **에이전트의 종합** (분리 설계서 §2.2):

```
combined = sqrt( intrinsic × effective )          # 기하평균
escalate if combined < τ,   τ = 0.45              # 사전 확정
```

기하평균을 쓰는 이유: 한쪽이 낮으면 전체가 낮아진다. 산술평균은 "이번엔 확신 없지만 평소 잘 맞으니 간다"를 허용하는데, 그건 에스컬레이션이 필요한 바로 그 상황이다.

**τ = 0.45 고정.** 실험 전에 확정하고 절대 조정하지 않는다. 조정하면 개입 횟수를 원하는 대로 만들 수 있어 결과가 무의미해진다. τ 민감도는 **사후 분석**으로 별도 보고한다 (`decisions.json`에 `combined`를 기록해 두었으므로 재실행 없이 τ를 바꿔 곡선을 그릴 수 있다).

**에피소드 간 신뢰도 유지 여부** — 두 모드를 모두 지원하고 실험 변수로 삼는다.

| 모드 | `reliability.json` | 보이는 것 |
|---|---|---|
| `cold` | 시나리오마다 초기화 | 단일 에피소드 내 적응 |
| `warm` | 전체 실행에 걸쳐 누적 | **장기 자기 개선** (논문의 §5 주장) |

주 결과는 `warm`. `cold`는 대조군.

# 6.3 도구 설명 수위 (§9 8번)

분리 설계서의 지적이 정확하다. MCP는 도구 설명을 LLM 컨텍스트에 그대로 넣으므로, `"평시 효율 우수"`는 사실상 프롬프트다.

**두 벌을 `mcp/policy/descriptions.py`에 두고 환경변수로 전환한다.**

```python
DESC = {
  "minimal": {
    "rule_based":    "임계값 기반 배분. 상황 라벨을 입력으로 받는다.",
    "lstm_forecast": "시계열 모델 기반 배분. 관측 이력 10스텝 필요.",
    "dqn":           "강화학습 정책 기반 배분.",
  },
  "advisory": {
    "rule_based":    "이용률 임계값 기반. 항상 가용, 보수적.",
    "lstm_forecast": "시계열 예측 기반. 평시 효율 우수.",
    "dqn":           "강화학습 정책. 학습 분포 내에서 우수.",
  },
}
MODE = os.environ.get("SLICE_DESC_MODE", "minimal")
```

`minimal`판은 **무엇을 하는지와 전제조건만** 말하고 **언제 쓰라는 말을 하지 않는다.** `lstm_forecast`의 `"이력 10스텝 필요"`는 조언이 아니라 호출 규약이므로 남긴다.

**주 실험은 `minimal`로 돌린다.** `advisory`는 비교 실행으로 붙인다.

- 두 조건의 정책 선택 분포가 비슷 → 에이전트가 관측으로 판단했다는 증거
- 크게 다름 → 설명에 이끌렸다는 증거이며, 이것도 **보고할 가치가 있는 결과**다 (MCP 기반 에이전트 설계의 일반 교훈)

어느 쪽이든 §9 8번이 위험에서 기여로 바뀐다. `desc_mode`를 `decisions.json`의 `config`에 기록한다.
