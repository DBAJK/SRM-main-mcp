# 1.5 도구 계약 검증 — 값 유실 9건

정정 A~K가 **기존 코드**의 문제였다면, 이 절은 **`TOOLS.md`의 도구 계약 자체**를 검증한 결과다. 도구 21개의 모든 입력 필드에 대해 *"이 값을 누가 생산하는가"* 를, 모든 출력 필드에 대해 *"이 값을 누가 소비하는가"* 를 역추적했다.

**생산자 없는 소비 4건, 소비자 없는 생산 5건이 나왔다.** 전부 코드 버그가 아니라 **계약의 구멍**이며, 구현 전에 메우지 않으면 통합 시점에 드러난다.

# 근본 원인 — 세 가지 패턴

아홉 건이 무작위로 생긴 게 아니다. 서버를 나눈 방식에서 구조적으로 유도된다.

**패턴 1 — 호출 순서가 값의 가용 시점을 어긋나게 한다** (V5, V6)

`record_decision`(3단계)이 `apply_allocation`(4단계)보다 먼저다. 기록 시점에 "실제 적용된 값"은 아직 존재하지 않는다. 그런데 채점은 적용값 기준이다.

```
기록 시점 t:  요청 allocation = {0.20, 0.70, 0.10}    ← ④에 남는 것
적용 시점 t:  실제 allocation = {0.34, 0.49, 0.17}    ← 아무데도 안 남던 것
채점 시점 t+1: error는 적용값 기준 = 0.086
              요청값 기준이었다면      = 0.316        ← 4배 차이
```

같은 이유로 ④가 보는 `observation.violations`는 **직전 결정**의 결과라 1스텝 어긋난다.

> **판정법**: 도구 X의 출력이 도구 Y의 입력인데 **호출 순서가 Y → X**라면, 그 값은 유실된다. 순서를 바꾸거나, 나중에 그 값을 보는 제3자(여기서는 ⑤)가 채워 넣어야 한다.

**패턴 2 — 무상태 원칙이 누적값의 공급선을 끊는다** (V4)

②는 무상태이고 ⑤를 호출할 수 없다(서버 간 직접 호출 금지, §2.2). 그런데 `lstm_forecast`의 신뢰도 `exp(−3·ē)`에서 `ē`는 **누적 오차**다. ②가 원리적으로 알 수 없는 값을 식에 넣어 두었다.

해결은 §2.2의 원칙 그대로다 — **에이전트가 중계한다.** ⑤가 `recent_error`를 반환하고, 에이전트가 `propose_allocation`의 인자로 넘긴다. ②는 여전히 무상태다.

> **판정법**: 무상태 서버의 산출식에 "최근 N회", "누적", "평균" 같은 말이 들어가면 그 값은 반드시 **인자**여야 한다.

**패턴 3 — 식별자를 쓰기만 하고 발급하지 않는다** (V2, V3)

`decision_id = {run_id}-{step:04d}`라고 형식만 정하고 `run_id`를 발급하는 도구를 두지 않았다. 에스컬레이션도 마찬가지로 `escalation_id`만 주고 `decision_id`를 안 줘서, 그 스텝은 `report_outcome`을 호출할 방법이 없었다.

> **판정법**: 명세에 등장하는 모든 식별자에 대해 *"이걸 처음 만드는 도구가 무엇인가"* 를 답할 수 있어야 한다. 답이 없으면 유실이다.

# V2가 가장 위험한 이유

나머지 여덟 건은 지표가 틀리거나 분석이 제약되는 수준이다. **V2만 논증 자체를 무너뜨린다.**

에스컬레이션한 스텝은 정의상 **에이전트가 가장 자신 없던 스텝**이다. `decision_id`가 없어 채점되지 않으면 그 스텝들이 통계에서 통째로 빠진다.

```
proposed arm:  어려운 스텝 4개를 에스컬레이션 → 그 4개가 집계에서 제외
baseline arm:  에스컬레이션 없음 → 60개 전부 집계
```

**비교군마다 표본이 다르다.** `proposed`의 `sla_violations`가 낮게 나와도 그건 어려운 스텝을 빼고 센 결과다. 핵심 논증인 *"개입은 줄었는데 SLA 위반은 늘지 않았다"* 가 **편향된 표본 위에서 성립**한다. 심사에서 지적당하면 방어할 말이 없다.

→ `record_escalation`이 `escalation_id`와 `decision_id`를 **한 번의 호출로 둘 다** 발급한다. 나눠 두면 에이전트가 빠뜨릴 수 있다.

# 재발 방지 — 계약 검사

도구는 앞으로도 늘어난다(이미 20 → 21). 사람이 매번 역추적하면 또 놓친다.

**`docs/contract.json`에 기계가 읽을 수 있는 계약을 둔다.** 도구마다 필수 입력, 출력 필드, 그리고 각 필수 입력의 **생산자**를 명시한다.

```json
{"propose_allocation": {
   "server": "policy",
   "requires": {"observation": "observe.get_observation",
                "situation":   "AGENT",
                "recent_error":"feedback.get_reliability_table"},
   "produces": ["policy","allocation","confidence","in_distribution","status"]}}
```

`tools/check_contract.py`가 검사할 것:

1. 모든 필수 입력에 생산자가 있는가 (`AGENT` 명시 포함) → **V3, V4 유형 차단**
2. 생산자의 호출 순서가 소비자보다 **앞인가** → **V5, V6 유형 차단**
3. 명세에 등장하는 모든 식별자에 발급 도구가 있는가 → **V2 유형 차단**
4. `produces` 중 아무도 소비하지 않는 필드 목록 → **V7, V8 유형 경고** (의도적일 수 있으므로 경고)

**`AGENT`가 생산자인 값은 네 개뿐이고, 그 넷이 연구의 기여 지점 전체다** — `situation`, `confidence.combined`, 에스컬레이션 판단, 정책 선택. 이 목록이 늘어나면 에이전트가 해야 할 판단이 서버로 새고 있다는 뜻이므로, 검사기가 **넷을 넘으면 경고**하도록 한다.

소유는 C다. 목 서버와 같은 성격 — **계약의 실행 가능한 명세**이고, C는 A·B의 서버를 소비하는 쪽이라 불일치를 가장 먼저 만난다.

# W5가 가장 위험하다

**§1.5의 V3(`run_id` 부재)를 고치고도 절반만 해결했다.** `run_id`를 발급하게 만들었지만, **산출물 경로는 여전히 `data/decisions.json` 단일**이었다.

```
exp-baseline-normal-s0     → data/decisions.json  (덮어씀)
exp-arm1-normal-s0         → data/decisions.json  (덮어씀)
...60회...
                           → 마지막 1회분만 남음
```

`reset()`이 ①만 초기화한다는 점도 명시되지 않았다. ③의 벤더 레이팅과 ⑤의 신뢰도는 실행을 넘어 살아남는데, **그게 의도인지 버그인지 문서 어디에도 없었다.** `cold`/`warm` 모드는 §6.2에 있었으나 **파일 경로와 연결되지 않아 실행 불가능한 규약**이었다.

→ §5.0에 실행 생명주기를 명시했다. `runs/{run_id}/`로 분리하고, 서버별로 무엇이 초기화되고 무엇이 남는지 표로 고정했다.

# W1·W2·W3 — `capacity` 도입의 파급

정정 K는 ①에 용량을 넣는 것으로 끝나지 않았다. **조달이 실제로 동작하게 되자 그동안 무해했던 공백이 드러났다.**

- **W1**: 조달이 장식일 때는 `procure()`를 언제 부르든 상관없었다. 이제 `add_capacity`가 `step()` 뒤로 가면 조달한 스텝이 효과를 못 본다 — 에이전트 입장에서 *"샀는데 아무 일도 안 일어났다"* 가 되어 조달 학습이 왜곡된다.
- **W2**: 만료가 없을 때는 `expires_at_step`이 의미 없었다. 이제 ③이 그 값을 계산해야 하는데 **①과 별개 프로세스라 현재 스텝을 모른다.** 에이전트가 `current_step`을 넘겨야 한다.
- **W3**: 비용이 집계되지 않을 때는 단위가 무의미했다. 이제 `procurement_cost_total`이 논문 지표이므로 **시간당 단가 × 스텝 수**를 그대로 곱하면 4배 부풀려진다.

```
cost_total = cost × duration_steps × (MINUTES_PER_STEP / 60)
           = 250 × 10 × 0.25 = 625.0        # 2500.0 이 아니다
```

> **교훈**: 죽은 기능은 계약의 구멍을 감춘다. 정정 K로 ③이 살아나자 W1·W2·W3가 동시에 드러났다. 1차 범위에서 제외한 `dqn`도 2차에 넣는 순간 같은 일이 일어날 것이다.

# W6 — V4를 고치면서 만든 새 구멍

§1.5의 V4를 고쳐 `propose_allocation`에 `recent_error`(스칼라)를 넣었다. 그런데 `compare_policies`는 **전 정책을 동시에 평가**한다. 스칼라를 받으면 모든 정책이 같은 오차 이력을 공유하는 셈이라 신뢰도 비교가 무의미해진다.

→ `compare_policies`는 `recent_errors: {policy: float}` 딕셔너리를 받는다. ⑤의 `get_reliability_table()` 출력을 그대로 넘기면 된다.

> **수정이 새 구멍을 만든다.** W6은 V4의 직접적 부산물이다. §1.5의 계약 검사기(`check_contract.py`)를 **수정할 때마다** 돌려야 하는 이유다.
